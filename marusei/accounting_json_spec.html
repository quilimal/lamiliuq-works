マルセイシリーズ バックアップJSON仕様書

版数：v2.0 制定日：2026-06-19 適用：マルセイ会計 build 18〜

1 仕様概要

本仕様書は、マルセイシリーズ（マルセイ会計・マルセイ棚卸・マルセイミニレジ）が出力するバックアップJSONファイルのデータ構造および互換ルールを定義する。真正性の検証方式については別文書「マルセイ会計 バックアップ真正性仕様書 v1.0」を参照すること。

v2.0では以下の変更を行った。

✅
v2.0 変更点
① meta オブジェクトを追加しRFC3161タイムスタンプによる真正性を担保
② journals[].voidedBy を正式フィールドとして追加（優良な電子帳簿要件対応）
③ sha256 計算対象をmetaを除いた本体部分と定義
ℹ️
バックアップファイルの真正性仕様の詳細は別文書「マルセイ会計 バックアップ真正性仕様書 v1.0」を参照すること。

2 ルート構造

バックアップJSONのルートオブジェクトは以下の12キーで構成される。

ℹ️
version はバックアップ形式の版数（スキーマ変更時に更新）。appVersion はバックアップを出力したアプリの版数（毎リリースで更新）。両者は独立して管理される。 
{
  "meta":        {...},    // ✅ v2.0追加: 真正性・バージョン情報
  "version":     "2.0",
  "exportedAt":  "2026-06-19T12:00:00.000Z",
  "appVersion":  "2026.0619.18",
  "settings":    {...},
  "accounts":    [...],
  "subAccounts": [...],
  "partners":    [...],
  "banks":       [...],
  "journals":    [...],
  "fixedAssets": [...],
  "diaries":     [...]
}
キー型説明
metaobject真正性情報（sha256・TST）v2.0
versionstringバックアップ形式バージョン。現行: "2.0"
exportedAtstringエクスポート日時（ISO8601 UTC）
appVersionstringマルセイ会計のアプリバージョン
settingsobjectユーザー設定
accountsarrayユーザー追加科目（プリセット科目は除外）
subAccountsarray補助科目
partnersarray得意先
banksarray金融機関
journalsarray仕訳（削除済み・編集前を含む全件）
fixedAssetsarray固定資産台帳（削除済みを含む全件）
diariesarrayミニ日記帳
⚠️
journals には現役仕訳に加え、削除済み・編集前・再決算により無効化された仕訳も含めて全件を出力する。
帳簿集計・残高計算・申告計算では、必ず voidedBy == null の仕訳のみを対象とすること。

3 meta オブジェクト

RFC3161タイムスタンプによる真正性を保証するフィールド群。

"meta": {
  "sha256":  "a3f1b2...",  // metaを除いた本体のSHA-256（hex小文字）
  "tst":     "MIIHbg...",  // RFC3161 TSTのBase64エンコード
  "tsaUrl":  "http://timestamp.digicert.com"
}
キー型説明
sha256stringmetaを除いたJSON本体（正規化済み）のSHA-256ハッシュ値（16進数小文字64文字）
tststringDigiCert TSAが発行したタイムスタンプトークン（DER→Base64）
tsaUrlstring使用したTSAのエンドポイントURL
ℹ️
sha256 の計算対象は meta キーを除いたJSONオブジェクト全体をキーソート・余分な空白除去した正規化文字列（UTF-8）とする。
これによりTSTをmetaに後から埋め込んでもハッシュ値が変化しない設計となっている。

5 accounts / subAccounts / partners / banks

ℹ️
accounts はユーザー追加科目のみ。プリセット科目（AccountStore.isPresetAccount() が true を返すもの）は除外される。 
"accounts": [{ "code": "800", "name": "消耗品費" }]

"subAccounts": [{
  "code":       "800A",
  "name":       "自宅兼事務所",
  "parentCode": "800",
  "rate":       "0.6"   // Decimal → string
}]

"partners": [{
  "tag":           "a",
  "name":          "山田商店",
  "invoiceNumber": "T1234567890123"
}]

"banks": [{ "tag": "a", "name": "みずほ銀行" }]
⚠️
【設計方針】得意先は名前で保持する
partners[].name はJournal側でも名前のまま保持される（旧名も記録として残す設計）。社名変更時も旧名での仕訳が記録に残るため、復元・履歴追跡が正確に行える。タグIDでは照合しないこと。

taxType の値一覧

値意味

8%軽減税率（インボイスあり）
10%（イ無）標準税率（インボイスなし）
8%（イ無）軽減税率（インボイスなし）
非課税非課税取引
不課税不課税取引

invoiceStatus の扱い

ℹ️
invoiceStatus は v1.9 以降 taxType に統合されたが、出力は継続・読み込みは互換保持とする。
復元時は decodeIfPresent で読み込み、存在しない場合は "qualified" をデフォルトとする。新規実装では taxType を正とし、invoiceStatus は参照しないこと。

sha256正規化ルール

正規化の詳細手順は「マルセイ会計 バックアップ真正性仕様書」を参照すること。最小限のルールを以下に示す。

項目ルール
対象meta キーを除いたJSONオブジェクト全体
キー順序アルファベット昇順でソート（ネストも再帰的に適用）
空白キーと値の間・要素間の余分な空白・改行を除去
配列順序変更しない（元の順序を保持）
nullnull リテラルとして出力
エンコードUTF-8

↳ journals[].voidedBy 仕様

優良な電子帳簿要件に対応するフィールド。訂正・削除・再決算の履歴を記録する。

⚠️
生成ヘルパーを必ず使用すること。インライン文字列での直接構築は禁止。
Swift: Journal.makeDeletedVoidedBy() / makeReplacedVoidedBy(newID:) / makeAutoVoidedBy()
💡
D_ は「元仕訳が無効化された」ことを表す接頭辞であり、単純削除と編集置換の両方に用いる。両者の区別は末尾の新仕訳IDの有無で判定する（空文字 = 削除、IDあり = 編集）。
状態値例
現役（有効） null null
削除 D_ + base62(unixtime, 6桁) + _ D_A1B2C3_
編集（修正） D_ + base62(unixtime, 6桁) + _ + 新仕訳ID D_A1B2C3_xK9mP2Q7
再決算による自動無効化 R_ + base62(unixtime, 6桁) + _ R_A1B2C3_

base62タイムスタンプ

Unix時間（秒）をbase62（0-9A-Za-z）で6桁表現したもの。IDGenerator.currentTimestampBase62() で生成する。

編集の連鎖例（A→B→C）

// 仕訳A（元の仕訳）: Bに置き換えられた
{ "id": "A0000001", "voidedBy": "D_A1B2C3_B0000001" }

// 仕訳B（Aの編集版）: Cに置き換えられた
{ "id": "B0000001", "voidedBy": "D_D4E5F6_C0000001" }

// 仕訳C（現役・最新版）
{ "id": "C0000001", "voidedBy": null }

9 生成・検証フロー

生成フロー（通信必須）

1
JSONを生成

帳簿データをJSONに変換。meta.tst は空文字とする。

2
SHA-256を計算

meta を除いたJSON本体（キーソート・余白除去済み）のSHA-256ハッシュを計算。

3
RFC3161リクエスト送信

DigiCert（http://timestamp.digicert.com）にSHA-256ハッシュを送信。

4
TSTを受信・埋め込み

TSTをBase64エンコードし meta.tst に埋め込む。

5
ファイルを提供

完成JSONをユーザーに共有（共有シート / Files.app）。

検証フロー

1
JSONを読み込み

meta フィールドを取り出す。

2
SHA-256を再計算

metaを除いた本体のSHA-256を計算し meta.sha256 と比較。不一致 → 改ざん検知。

3
TSTを検証

Base64デコード→DER解析→TSTのハッシュとDigiCert署名を検証。

4
真正性確認

全検証通過 → 「バックアップ真正性確認済み」と判定。

10 後方互換ルール

ルール内容
フィールド追加新フィールドは常にオプション（decodeIfPresent）とし、旧バックアップでキーが存在しない場合はデフォルト値を使用する
フィールド削除廃止フィールドは削除せず出力を停止するのみ。読み込み側では無視する
voidedByなし旧バックアップの voidedBy キーが存在しない場合は nil（現役）として扱う
diariesなしdiaries キーが存在しない場合は空配列として扱う
metaなし旧バックアップに meta キーが存在しない場合は真正性未検証として扱う（復元は可能）
version判定復元時は version を参照してマイグレーション処理を分岐する
⚠️
廃止フィールド（partner・subAccount・provisionalTaxReceived・provisionalTaxPaid・taxJournalID・parentJournalID）は読み込み時に無視する。
